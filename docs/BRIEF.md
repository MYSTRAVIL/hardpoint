# Hardpoint: kickstart brief

This brief starts the Hardpoint repo: a Svelte 5 component library that is the user's shared app design system. Its look and motion come from Dan Neuenhaus's MONOLITH reel. The library takes the reel's style, not its content: the reel is a sci-fi logistics terminal, and its story (SYS BREACH, the MONOLITH brand, containers, yard maps) does not belong in general apps. The library must work in real apps on desktop and on phones. The brief was written in the moodboard repo, which keeps the source video and the analysis tools. Since 2026-11-09 this repo owns the brief and its evidence.

- **Name:** Hardpoint, after the mounting points on a military airframe where equipment attaches. It fits the military/high-tech goal and the joined-panel structure.
- **Package:** `@mystravil/hardpoint` on the public npm registry, MIT licensed (the fonts keep the SIL Open Font License). The user chose the scoped name, MIT and version 0.1.0 on 2026-11-11. 0.1.0 went out on 2026-11-11 (tag `v0.1.0`), and 0.2.0 the same day (tag `v0.2.0`), with the eight parts omp-remote asked for. 0.2.1 (2026-11-12, tag `v0.2.1`) only adds the repository link; it is the first version the release workflow published, with a provenance attestation. It needs Svelte 5.57 or newer.
- **Repo:** master lives on the user's private Forgejo (`origin`). On 2026-11-12 the user made the source public on GitHub, [MYSTRAVIL/hardpoint](https://github.com/MYSTRAVIL/hardpoint), so that releases publish automatically: npm's trusted publishing accepts only hosted CI such as GitHub Actions, and every other path needs a person to pass 2FA for each release. GitHub gets snapshots of master without the agent memory, handoffs, overnight runs and the reel's frames; a `v*` tag there runs the release gates and publishes (`.github/workflows/release.yml`).

Read in this order:

1. This brief. [The style](#the-style) and [Apps and phones](#apps-and-phones) are the spec.
2. `omp-remote/docs/ui-language/BRIEF.md`: the approved appearance rules (colour, type, geometry, states). This brief adds to them and corrects one border token.
3. [ux-research.md](ux-research.md): published UI/UX guidance for AI agents and the primary standards (WCAG 2.2, Material 3, Apple HIG, MDN), with the draft rules tested against them.
4. [elements-da3.md](elements-da3.md) and [measurements-da3.md](measurements-da3.md): what the reel shows, element by element, with pixel measurements. They are evidence for how a rule looks and moves, not a build list. Their `home` column is superseded.
5. [reference/da3/](reference/da3/): 30 colour-accurate 1080x608 frames cited by both files.

## Decisions (user, 2026-11-09)

- The library is the shared app design system, not a separate expressive kit.
- **Style, not replica.** Apply the reel's visual and motion language to ordinary app UI. Do not reproduce its screens, story or branding. A component exists because apps need it, not because the reel shows it.
- **Real apps, desktop and phone.** Phone layouts are a requirement. Where the reel's poster-like choices (tiny caps, empty space, long animations) conflict with usability, the app rule wins and the reel's look moves into details or into the opt-in motion layer.
- Base components are quiet by default: the reel's grammar without its motion. The reel's motion is an opt-in `expressive` layer.
- No hue is a brand colour. The user retired the Coral red accent on 2026-09-24 because a red brand colour read as an error, and restated it for this reel's orange. Wherever the reel uses orange, the library uses titanium, or a status hue only where the element means that status.
- Behaviour comes from headless [Bits UI](https://www.bits-ui.com/); the look and the motion are authored. A styled kit is not re-skinned: the 2026-09-15 studies swapped tokens over a conventional layout and were rejected as generic.
- Packaging starts now. This replaces the earlier gate that waited for a second consuming app.
- **Dark only for now.** The first milestone shipped the dark palette alone. Light mode followed on 2026-11-11 ([Second milestone](#second-milestone-set-2026-11-11)); dark stays the default.
- **Reel grammar in the base** (after reviewing step 1). The first foundations looked like the September study, because each app correction in this brief had moved a reel trait back toward omp-remote. The user chose the reel's grammar in an app-safe form: solid titanium blocks for actions and tags, a filled header band on tables, no row dividers by default, caps view titles, Geist Mono for data and a large display subject. Phone rules still win.
- **No cut corners.** Every box is square, as in the reel. Cut corners were the September study's signature.
- **Hardpoint leads.** Hardpoint sets the language. omp-remote may adopt it later and change its look; the two share the colour tokens and the phone patterns.
- The user left the remaining design choices to the assistant. They are recorded under [Decided](#decided) with their reasons.

## The style

Each rule says what the library keeps from the reel and how it changes for apps. Element ids (`da3-NN`) point into [elements-da3.md](elements-da3.md); the evidence for each change is in [ux-research.md](ux-research.md#draft-rules-tested).

### Visual

1. **Two inks on black.** The reel uses one light ink for everything. Apps need a second tone for supporting text, or every level of hierarchy has to come from size, which costs space. Use `--text` and `--muted` and nothing else; no third grey (da3-45, da3-53).
2. **Solid blocks mark actions.** The reel fills its buttons, selects and tags with a light block (da3-41, 44, 50, 51, 62). Buttons are square titanium blocks with black caps labels; a button that opens another view ends in a small ▸ (da3-50, da3-62). Filling every button would make every control look primary, so a view shows one group of solid blocks: a single primary action, or the header's row of equal-weight page actions. Other actions are outlined (1 px `--border-control`, titanium label) or plain text. Tags are small solid titanium blocks with black caps; a tag may sit above a block to name it, as UNIT ID names the identifier (da3-51). Inputs and selects stay black wells with a visible boundary, because a filled select reads as a button. Selection is never a fill: a selected row, item or tab gets a 3 px titanium edge marker and a `--surface-selected` tint, with its text unchanged. Hover and press never darken a selected row.
3. **One display subject per view.** The reel sets one huge subject over small text (da3-52, da3-65). A detail view gives its subject the display size: an identifier in Geist Mono, or a key figure in Geist with tabular numbers, at 32 to 56 px through `clamp()`. Names a user wrote never take the display size; they stay at the page-title size. The view title lives in the header (rule 9).
4. **Tracked caps for fixed labels; three Geist faces with fixed roles.** Caps with 0.05 to 0.08 em tracking set view titles, buttons, tabs, tags, column headers, field labels, key-value labels and occasional section labels, at 12 px or more. View titles are fixed strings the app defines, so they take caps in the header, as in the reel (da3-40). Headings inside content, menu and list items, body text, messages, errors and any user data stay as written and are never transformed. Set caps through a `--label-transform` token so an app or locale can turn it off. Geist sets reading text, headings, messages, form input and list item titles; its numbers use `tabular-nums`. Geist Mono sets data, as in the reel (da3-45, da3-53, da3-60): table cells, key-value values, timeline lines, identifiers, timestamps, hashes and code, with case untouched. Geist Pixel Square is a display accent, as in the reel, where pixel glyphs appear only at moments of change (da3-17): the brand wordmark, at most one short fixed display line per screen (an empty-state or error headline) at 26.32 px or larger, the stepped spinner and the decode noise. It never sets labels, values, body text, page titles or user data. Key figures stay in Geist, because Geist Pixel has no tabular figures and a ticking value would change width.
5. **Plain labels over fields.** The reel puts a filled chip above every field (da3-23). That makes labels louder than the input and adds height. Use a plain caps label above each field; chips are only for tags.
6. **Structure from alignment.** Tables have one filled header band in `--surface-band` with caps column labels, then rows of Geist Mono on a tight even pitch, with no zebra stripes, cell borders or row dividers (da3-42, da3-45). The band and the row tints reach `--bleed` past the text edge into the gutter, so text keeps the page edge while fills extend further (da3-43). Apps add a hover row tint on pointer devices, right-aligned tabular numbers and a sticky header; a `ruled` variant adds 1 px row dividers for long dense tables. Key-value lists keep a caps label column and a Geist Mono value column without separators (da3-53).
7. **Discrete shapes.** Progress is a bar of separate segments that follows real progress (da3-38). Timeline nodes are squares on a 2 px rail (da3-60). The spinner steps through `|`, `/`, `-` and `\` in Geist Pixel Square, 167 ms per state, which reproduces the reel's stair-stepped diagonals (da3-10). It is `aria-hidden` beside a text label and appears only after 300 ms.
8. **Hairline frames for media.** Images and diagrams sit in a 1 px frame with a few small `+` registration marks (da3-55, da3-61; [t26.67](reference/da3/t26.67s.jpg)). Text blocks get no frame. Controls get a boundary of at least 3:1 (see [Tokens](#tokens)).
9. **A fixed, compact shell; black from restraint, not margins.** One header row stays in place: the wordmark at the left, the view title in caps centred on the page, and the page controls on the right (da3-40). No rule under it. The wordmark and the controls take equal side columns, so the title centres; below 1200 px the controls move to their own row under the header, and on phones the title follows the wordmark when there is no room to centre it. Every page shares the same edges (da3-43). The reel's black comes from huge margins; in apps it comes from having no cards, boxes or fills around content, and from grouping by space (gap between groups at least twice the gap within one). Content uses the available width.

### Motion

The reel's timing suits a video watched once. App motion runs hundreds of times a day, so every animation passes a frequency check first, in three tiers (the research's gate; the user, 2026-11-11, allowed motion that is "short enough to be noticed but not get in the way of daily usage"). An action used constantly, about 100 times a day or more, gets no animation. An action used tens of times a day gets short, subtle motion: a fade of opacity or colour of 150 ms or less, never a move. A rare moment gets normal or expressive motion. Three things stay out at every tier: motion that repeats on every key press (moving a highlight, typeahead, arrow keys between tabs), motion that moves content someone is reading, and selection indicators that slide (rule 3). Opening and closing an overlay animates the same way whichever input opened it (decided 2026-11-09: the input method does not make an open more frequent). One frame of the reel is 41.67 ms.

1. **Page changes cut.** The old content drops out, the shell stays, the new page appears (da3-49). No cross-fades and no slide transitions between routes.
2. **Blocks, then content, only while waiting.** If data takes more than 300 ms, skeleton blocks that mirror the final layout fill the page, and content replaces them as it arrives. This is the reel's build sequence, applied to real loading. Cached or fast content appears at once.
3. **Selection snaps.** Selection jumps to its new place without sliding (da3-36, da3-48). This is also the right behaviour for frequent actions.
4. **Responses are fast and ease out.** Press feedback 100 ms or less; hover 100 to 150 ms, pointer devices only; menus, popovers and tooltips 150 to 200 ms; dialogs and sheets 200 to 300 ms. Exits are about 70 percent of the entrance. Use `--settle` (ease-out). Never ease-in on a response.
5. **Numbers tick on change only.** A value that changes through a user action or a live update ticks from old to new in about 400 ms with tabular figures. Numbers never count up on load: the reel's 2.1 s roll-up hides the value (da3-47, da3-67).

The `expressive` layer adds, for infrequent moments only (first load of a view in a session, a success, an empty state filling):

6. **Decode-in.** Short labels and titles resolve from coarse blocks through glyph noise to clean text in 5 to 6 frames, each element on its own clock (da3-16). The noise is drawn in Geist Pixel Square, as the reel's is (da3-17). It sits over the final text's reserved box, because Geist Pixel is proportional and the line would otherwise change width. Never on values, body text, user content or anything that updates. The accessible name always holds the final text. **Lab only** (the user, 2026-11-10): built and judged on `/motion`, it reads as a gimmick in real apps, where a fade works better. No component uses it and the package does not ship it; the code stays beside the `/motion` demo as a reference.
7. **Stagger.** The first 6 to 8 items enter 30 to 40 ms apart, 300 ms in total at most. Never on lists that re-render through filtering, sorting or paging (da3-32, da3-46).
8. **Flicker-on.** An element may switch on with a single off frame on first appearance (da3-11). No repeated blinking, never more than three flashes in a second, no full-screen white flashes. The reel's triple blink on selection is dropped. **Lab only** (the user, 2026-11-11): built and compared with a plain fade on `/motion`. No component uses it and the package does not ship it; the code stays beside the `/motion` demo (`src/routes/motion/flicker.ts`).
9. **The reel's slide curve.** `cubic-bezier(.87,0,.13,1)` gives the mechanical start-stop of the reel. Use it only for non-interactive moves of large elements, at 300 to 400 ms, never in response to input (the reel's 650 to 800 ms reads as lag in apps). No component uses it, so `--slide` and `--dur-slide` left `tokens.css` on 2026-11-11; a component that needs the curve brings them back.
10. **Image resolve.** An image that is actually loading may show as a pixelated block ramp that sharpens when it arrives (da3-57), ending within 300 ms of load. **Decided by the user on 2026-11-11:** an image resolves only in the expressive tier. Everywhere else, in the quiet tier and with reduced motion, it fades in over its skeleton. `MediaImage` builds both.

Reduced motion makes motion gentler, not broken: slides and image resolves become short opacity fades, and decode, stagger, flicker and number ticks are off. Spinners and progress stay.

## Apps and phones

Phones are a requirement. omp-remote, the first app on this design language, already solves most of this in `apps/web/public/styles.css`; take its patterns rather than inventing new ones.

- **Breakpoints.** Compact below 600 px, medium 600 to 899, expanded 900 to 1199, large from 1200. These are omp-remote's; compact matches Material 3. Lay out by width, not by device.
- **Touch targets.** On coarse pointers every interactive element has a hit area of at least 44 by 44 px, with 8 px between targets. A visible control may be smaller if padding or a pseudo-element extends the hit area. Never below 24 px anywhere (WCAG 2.5.8).
- **Density.** A `--density` multiplier scales vertical rhythm (omp-remote: 1, compact 0.625). Control heights are 44 px on coarse pointers, 36 px on fine pointers and 32 px on fine pointers in compact density. Compact density never reduces touch targets.
- **Type on phones.** Inputs are 16 px at every width, or iOS zooms on focus. Body text is 16 px on phones; 14 px is allowed for dense UI on fine pointers. Display sizes use `clamp()` so they shrink on phones. Text must survive 200 percent zoom and WCAG text-spacing overrides.
- **Viewport.** `viewport-fit=cover`; `env(safe-area-inset-*)` on every edge-anchored bar, sheet and floating element; `100dvh` (or `svh` for minimum heights) instead of `100vh`; never `maximum-scale=1`; `overscroll-behavior: contain` inside overlays; `touch-action: manipulation` on controls. Content must reflow at 320 px wide.
- **Hover.** Hover styles and hover-revealed actions only under `@media (hover: hover) and (pointer: fine)`. Every hover-revealed action also has a visible or menu path on touch. Touch gets immediate `:active` feedback.
- **Navigation.** Compact: a bottom bar with three to five destinations, or a drawer from the header. Medium and up: a rail or sidebar. The header is compact on phones (48 to 56 px plus the top safe area).
- **Overlays.** Compact: menus, pickers and short confirmations open as bottom sheets with a close button, an initial height of at most half the screen, and swipe to dismiss. Long or complex forms open as full-screen dialogs. Medium and up: popovers and centred dialogs. One overlay component should pick the form by breakpoint, on top of Bits UI's Dialog and Popover.
- **Choices.** A single choice from a short fixed list is a native `<select>`, so phones keep their own picker (as in omp-remote). Bits UI Select and Combobox are for searchable or rich options, and open as a sheet on compact widths.
- **Wide data.** On compact widths a table becomes a stacked list: the primary field as the row title, two or three key fields as key-value lines, and the whole row as the 44 px target. True data grids may scroll horizontally instead, with a sticky first column and a visible scroll edge.
- **Keyboard.** Keep the focused field visible above the on-screen keyboard. Sticky composers and action bars follow the visual viewport (`interactive-widget=resizes-content` or the VisualViewport API). Set `scroll-padding` for sticky headers.
- **Forms.** Labels above fields, never placeholder-only. Errors inline below the field with an icon and text, linked by `aria-describedby`, set `aria-invalid`, never a red border alone. Validate on blur and on submit; on submit focus the first error. Never disable the submit button to signal errors. Set `inputmode`, `autocomplete` and `enterkeyhint`.
- **States.** Every data view designs its empty, loading, error and sparse states. Empty states offer one clear next action. Errors say how to fix the problem, next to where it happened.

- **Boundary contrast.** WCAG 1.4.11 asks 3:1 for the boundary that identifies a control. `--border` at 2.5:1 fails that, so it stays on dividers only and controls use `--border-control`. omp-remote currently draws input borders in `--border`; tell that app's owner rather than editing it from here.
- **Type scale (proposal).** 12 caps label · 13 caption · 14 dense UI (fine pointers) · 16 body and inputs · 20 section title · 24 page title (20 on compact) · 20 caps view title in the header (16 on compact) · 32 to 56 display for the subject, via `clamp()` · Geist Pixel at 26.32 or 52.63 px. Weight 400 or more below 18 px; Geist display sizes take -0.01 to -0.02 em tracking.
- **Line breaks** (added 2026-11-11). base.css gives `p`, `li`, `dd`, `blockquote` and `figcaption` `text-wrap-style: pretty`, so reading text never ends on a lone word, and headings and the title roles (`.hp-page-title`, `.hp-section-title`, `.hp-display`) `text-wrap-style: balance`; the balance rule comes second, so a title set on a `<p>` balances. Both use `:where()`. The longhand leaves the wrap mode alone, so a `nowrap` or truncating parent still holds; browsers without it wrap as before.
- **Inline code** (added 2026-11-11). A `code`, `kbd` or `samp` that is a direct child of `p`, `li`, `blockquote` or `figcaption` is `inline-block` with `overflow-wrap: anywhere`, so a token moves to the next line whole and never splits at a hyphen or a space; before, the docs split 52 tokens such as `--skeleton-delay` across lines at 320, 390 and 1440 px, and now none. Punctuation stays with the token (no break after `(` or before `)`, `,` and `.`). A token wider than the line wraps inside its own box, at a hyphen or space first, so it never overflows; then the punctuation after it starts the next line. No docs token is that long at 320 px. Only direct children: an atomic box in a truncating cell (a Table `dd`) would vanish whole into the ellipsis, and a link's underline does not reach into one.
- **Reading measure** (added 2026-11-11). `:where(p)` stops at `--measure`: 512 px at 16 px, 416 px for a 13 px hint. EmptyState, ErrorState and the docs pages use the token. It is in `em`, not `ch`: Geist's zero is 0.663 em wide, so the old 60ch held about 86 characters and 68ch about 97, and `ch` changes width when Geist replaces the fallback. The research range is 60 to 75 characters ([ux-research.md](ux-research.md)). `ch` stays right for Geist Mono data columns, where it is the glyph width.
- **Prose styles** (added 2026-11-11 at omp-remote's request, for rendered markdown or sanitised HTML an app cannot scope styles into). `.hp-prose` in base.css: the app puts the class on the container. Every rule is `:where(.hp-prose …)`, so an app's rule wins. Blocks do not cap at `--measure`; the container's width decides, so the app gives it a readable one. Text is 16 px on 24 px lines; gaps, indents, code and line heights are in `em` and follow the container's size. h1 and h2 take the page-title and section-title tokens, h3 to h6 stay at body size and step down in weight (600, 500), then to `--muted`, and headings are as written, never caps. Gaps are 1em between blocks, 0.5em under a heading and 0.25em between list items. `ul` markers are squares and `ol` markers tabular figures, both in `--muted`. A task-list checkbox draws as the Checkbox box in its disabled form, a `--border` edge with a `--muted` mark, drawn with `clip-path`, so it needs no image. A quote is a 3 px `--border` edge with muted text, and `hr` is a 1 px `--border` line. Inline code is 0.875em. Images are blocks, at most the container's width.
- **Prose code and tables.** A code block is Geist Mono at 0.875em on 20 px lines and scrolls sideways inside a 1 px `--border` hairline with no fill (the assistant's decision, 2026-11-11: `--surface-hover` is invisible on black, `--surface-band` is too heavy under a long listing, and the hairline reads in both themes and shows where the scrolling area ends). A copy button goes in `.hp-prose-code` with the class `hp-prose-copy`: the wrapper draws the hairline, and the `pre` leaves the button a column of `--control-height` plus 8 px, so scrolled text never runs under it. That costs 44 px on a mouse and 52 px on touch, 18% of a 288 px column. The button is a sibling of the `pre`, so a renderer that replaces the `pre` keeps it. A table goes in `.hp-prose-scroll`, which scrolls sideways when the table is wider. Its header is as written in `--surface-band`, its cells are Geist in tabular figures, and a cell's `align` attribute sets its alignment. Every row has a 1 px `--border` divider, because cells that wrap into several lines need one (the assistant's decision, 2026-11-11); there is no zebra. Cells and code blocks use `overflow-wrap: normal`, so they scroll instead of breaking mid-word. The app adds `tabindex="0"` to scrolling blocks and wrappers.
- **Fallback faces** (added 2026-11-11). `fonts.css` defines local faces sized to Geist, so text keeps its width and baseline when the real face arrives (`font-display: swap`): `Geist Fallback Arial` (Arial, Liberation Sans or Arimo at 102.8%), `Geist Fallback Roboto` (Android's Roboto at 103.1%) and `Geist Mono Fallback` (Consolas at 109.13%; Menlo, Courier New and Android's monospace are within 0.3% of Geist Mono's 0.6 em advance already). The overrides set Geist's ascent and descent at that size. Each `size-adjust` is the width ratio measured in Chromium over every Geist text node of 13 docs pages at 1440 and 390 px. A separate Arial face for weight 500 measured worse (caps want 95.6%, lowercase 105.9%), so each font has one face; during the swap, caps labels run about 7% wide. With the fonts held back 2.5 s, the layout shift at the swap, summed over 8 docs pages, fell from 0.50 to 0.003 at 1440 px and from 0.80 to 0.09 at 390 px. An app that skips `fonts.css` skips the fallbacks too and gets the generic family. The Roboto face is unverified on a device.
- **Icon alignment** (settled 2026-11-11). An icon beside text centres on the line box of the text's first line. Geist's caps centre in that box by its metrics, but Chromium rounds the ascent and descent to whole pixels, so caps sit up to 0.68 px high (16 px on 24 px lines) and the icons beside them inherit it. That stays as it is: it is under a pixel, and a fix would need a separate offset for each size and line height. Icons do not centre on the x-height, so beside lowercase text they sit up to 1.7 px above the x-height's centre. A measurement of every pairing found two real faults, both fixed:
  - **Timeline node.** It sat at `top: 4px`, right for 20 px lines but 2 px high on touch, where lines are 24 px. It now centres on the first line with `1lh`, and the rail follows it; desktop pixels are unchanged.
  - **Select text.** A native select, the Select trigger and the compact Combobox trigger set their text 1 px higher than a text field's, at every pixel ratio from 1 to 3. They took the inherited 24 px line height, while a text field centres its glyph box. `.hp-well` now sets `line-height: normal`, so every well centres its glyph box: caps sit at the same height in all five well kinds at pixel ratios 1, 1.25, 1.5, 2, 2.625 and 3. Only the text inside select wells moved; text fields are pixel-identical.
- **Spacing.** A 4 px grid. Gaps between groups are at least twice the gap within a group.
- **Added in step 1.** `tokens.css` also carries `--type-*` (the scale above; `--type-view` is the caps view title), `--space-1` to `--space-16`, `--gutter` (page edges: 16 px compact, 24 px medium, 32 px from 900 px), `--header-height` (56 px, used for the sticky band and `scroll-padding`), `--control-height` (36 px on fine pointers, 32 px in compact density, 44 px on coarse pointers), `--hit-target` (24 px; 44 px on coarse pointers), and omp-remote's `--surface-raised`, `--scrim`, `--select-chevron` and `--status-mark`. `[data-density="compact"]` works on any subtree, so a dense table can sit in a comfortable page.
- **Ground and type.** The reel's ground is `#100D11`; keep literal `#000000`. The Geist family supplies all three faces and no other display face is added. The reel's 45 degree chamfered display caps (face not identified) are not reproduced: Geist has no chamfered face, and cut corners were dropped on 2026-11-09.
- **Crisp pixel text.** Geist Pixel Square draws on a module of 0.038 em (38 of 1000 units; caps are 19 modules high). A module is a whole number of pixels only when the font size is a multiple of 26.32 px: 26.32 px gives 1 px modules and 19 px caps, 52.63 px gives 2 px modules. On screens with a device pixel ratio of 2 or more, half steps (39.47 px) also give whole device pixels. Other sizes blur the edges; check the result in the browser, because the baseline position matters too. Line heights of 32 and 63 px keep the top edge on a whole pixel; never centre pixel text in a box whose free space is odd. Measured 2026-11-09: on Windows, Chrome spreads every vertical edge over two pixels whatever the font's `gasp` table or CSS says (DirectWrite smooths horizontally); horizontal edges stay sharp. macOS, iOS and Android are not yet checked.
- **Geometry.** Square corners everywhere: no cut corners and no radii. Hairlines are 1 px.

## Architecture

```
src/lib/
  fonts.css      @font-face rules for the three faces and their size-matched fallbacks, exported as ./fonts.css
  tokens.css     framework-free tokens, exported as ./tokens.css
  base.css       focus, type roles, square blocks, exported as ./base.css
  components/    Svelte components on Bits UI primitives       → "."
  motion/        tier context, transitions                      → "./motion"
```

- **Motion tiers** (decided 2026-11-09). `<Motion tier="expressive">` from `@mystravil/hardpoint/motion` sets the tier for everything inside it; without it the tier is `quiet`. Components call `useMotion()` during initialisation; its `expressive` field is true only when the tier is expressive and the user has not asked for reduced motion. Quiet motion (rules 1 to 5) runs in both tiers; expressive effects (rules 6 to 10) check `expressive`. The app decides when a moment is expressive, for example the first load of a view in a session.
- **Motion tokens and transitions.** Durations live in `tokens.css`: `--dur-press` 80 ms, `--dur-hover` 120 ms, `--dur-pop` 160 / `--dur-pop-exit` 110 ms (menus, popovers, select lists, tooltips), `--dur-sheet` 240 / `--dur-sheet-exit` 170 ms (dialogs and sheets), for the stagger `--dur-enter` 150 ms and `--stagger-step` 30 ms, `--dur-reveal` 150 ms for content that crossfades in over skeletons (the user chose the fade over a cut on `/motion` on 2026-11-10), `--resolve-step` 42 ms for one of the five steps of an image resolve (MediaImage, expressive tier only; the user's choice of 2026-11-11), `--dur-expand` 120 ms for a Disclosure's content fading in (the user chose height snaps and content fades on 2026-11-11), four short-motion tokens for frequent actions, chosen by the user on `/motion` on 2026-11-11 over a snap (`--dur-mark` 80 ms for selection marks, `--dur-panel` 100 ms for a tab panel a pointer chose, `--dur-segment` 120 ms for progress and steps, `--dur-message` 120 ms for field errors), and `--dur-tick` 400 ms for number ticks. Two curves sit beside them: `--settle` for every response, and `--tick` (rule 5). `--tick` is `var(--settle)`: the user compared both curves on `/motion` on 2026-11-10 and chose the settle curve over the reel's counter curve, `cubic-bezier(0.37, 0, 0.63, 1)`. `curve()` reads it through the `var()`. The Svelte transitions `pop`, `sheet` and `fade` in `./motion` read these and `--settle` from the element, so an app that retunes a token retunes its transitions; each picks the exit duration on the way out. Under reduced motion `pop` and `sheet` fade without moving. The stagger is the `.hp-enter` class in `base.css` with `--i` set to the item's index: six items, 30 ms apart, done by 300 ms. LoadRegion reads `--dur-reveal` and `--settle` from its region when a load ends. MediaImage reads `--resolve-step`, `--dur-reveal` and `--settle` from its element when an image arrives. Disclosure reads `--dur-expand` and `--settle` from its element when it opens. Short motion fades opacity or colour on `--settle`, only on a change, never on a first render or a mount; it is quiet motion, so it runs in both tiers, and reduced motion keeps it. Marks, segments and the well's edge use CSS transitions, which never run on an element's first style; the tab panel and the error message fade through `components/internal/fade-in.ts`, which reads the token and `--settle` from the element and does nothing at 0 ms.
- **Bits UI and transitions.** Bits UI for Svelte 5 has no transition props. To animate a conditionally rendered part, set `forceMount` and render through the `child` snippet with `{#if open}`. Floating content (Popover, Select, DropdownMenu) also needs a wrapper element that spreads `wrapperProps`; the transition goes on the inner element, which carries `data-side`. Wrap this once per primitive; see [Bits UI transitions](https://bits-ui.com/docs/transitions).
- **CSS rules.** Transition only `transform`, `opacity` and colours; never layout properties, never `transition: all`. CSS transitions for interactive state, keyframes only for expressive entrances. Colour changes on hover and press are paint-only, so they may fade over `--dur-hover`; the first version of this rule allowed only transform and opacity, which would have forced an overlay element into every control.
- **Accessibility.** Text that decodes keeps its final string in the DOM and the accessibility tree, and the animated copy is `aria-hidden` (decode-in paints the real text transparent while it runs). An image that loads (MediaImage) is in the DOM and the accessibility tree with its `alt` from the moment it has a `src`, hidden only by opacity while it waits; its skeleton, mosaic and error caption are `aria-hidden`. Never animate inside a live region. Visible focus on every control; selection and focus look different.
- **Consumers** (decided 2026-11-10). omp-remote and topic-map move to Svelte and use the components. Neither runs SvelteKit (topic-map is Svelte and Vite with its own router; omp-remote builds with Bun), so nothing under `src/lib` imports `$app/*`, `$env/*` or `@sveltejs/kit`, and components take state such as the current route as props. Files in `src/lib` import each other by relative path, because `#lib` points at `src/lib`, which the package does not ship. `npm run check` enforces both. Hardpoint leads, so adopting it changes both apps' look: square corners and the reel grammar.

### Component conventions (decided 2026-11-09)

- **Files.** One component per file in `src/lib/components/`, PascalCase (`Button.svelte`). Parts of a family are separate files (`Table.svelte`, `Pagination.svelte`). Types a consumer needs are exported from the component's `<script module>`. `src/lib/index.ts` exports every component by name.
- **Props.** Runes and TypeScript. A component that renders one native element extends that element's attributes from `svelte/elements` and spreads the rest onto it, so `id`, `aria-*`, `data-*` and event handlers pass through. `class` is merged, never replaced. Two-way values are `$bindable` (`bind:value`, `bind:page`).
- **Variants.** One `variant` prop with a closed string union. The default is the quietest common form; Button defaults to `secondary`, because solid blocks are limited to one group per view.
- **State in attributes.** The root carries a stable `hp-<name>` class, and state is exposed as `data-*` (`data-variant`, `data-selected`) and ARIA. Styles key off those, so apps can target them.
- **Styles.** A scoped `<style>` in the component, tokens only: no literal colours, sizes off the 4 px grid, or durations. `:global()` only for parts Bits UI renders. Hover styles only under `(hover: hover) and (pointer: fine)`; `:active` feedback within `--dur-press`; heights from `--control-height`; hit areas of at least `--hit-target`; focus from `base.css`. Square corners.
- **Docs.** Each component has a route `/components/<name>` that shows every variant and state with neutral content.

   - **Decode-in** (lab only: built 2026-11-10 for motion rule 6, and judged by the user the same day as too gimmicky for real apps, so the package does not ship it and no component uses it). `useDecode()` in the route-local `src/routes/motion/decode.ts` returns `decode(options?)`, which makes an attachment. Call `useDecode()` during component initialisation, as `useMotion()`: the tier is the one around the calling component. Put `{@attach decode()}` on any element whose content is plain text, such as `<h1 class="hp-view-title" {@attach decode()}>{title}</h1>` or `<Button {@attach decode()}>Import</Button>`; Button and Tag pass attachments to their root through their rest props. The one option is `delay`, in whole frames, so a page can order its parts. It is an attachment, not a `Decode` component, because Button and Tag take their labels as `children` snippets, which a component with a `text` prop cannot take over, and because the element keeps its own markup, classes and truncation. An element with child elements (an icon beside a label, a `<strong>` in a title) shows its text at once; attach the decode to an element round the plain text instead. The sequence steps on `--decode-frame`, read from the element when the decode starts; it is not in `tokens.css`, so a decode uses 42 ms (one reel frame) unless the `/motion` tuning sets it. Frames 1 and 2 are solid blocks in `currentColor` over the text's cap band, new each frame: one to three bars, then a mosaic of half-height cells. Frames 3 to 5 hold one set of Geist Pixel Square noise: broken capitals and digits packed across each word, with half the punctuation dropped as a gap. Frame 6 is the clean text, about 250 ms after the first. Each element starts 0 to 2 whole frames late at random, plus its `delay`, and all its glyphs change together. It runs only when `useMotion().expressive` is true and only when the element mounts. An element the server rendered (it was on screen before hydration), an element inside a live region (`aria-live` other than `off`, or the role `status`, `log` or `alert`) and forced colours show the text at once. A text change after mount never decodes; a change during a decode ends it and shows the new text.
   - **Decode-in drawing.** The text stays in the DOM and in the accessibility tree and keeps its box: `-webkit-text-fill-color` and `text-decoration-color` paint it transparent while the decode runs. Blocks and noise draw in an `aria-hidden` layer appended to the element (`.hp-decode-layer`, `data-stage` wait | blocks | noise). It is a 0x0 absolutely positioned anchor holding a box over the text's line boxes, clipped to them and to any clipping parent below the layer's containing block, such as a truncated title, with pointer events off. The layer goes when the decode ends; focus never moves. Crisp pixels: the noise size is k × 26.32 px divided by the device pixel ratio, with k the smallest whole number (at least 1) whose 19-module capitals are as tall as the text's capitals. A 12 px label gets 26.32 px noise at a ratio of 1, 13.16 px at 2, 20.05 px at 2.625 and 17.54 px at 3. The 20 px title gets 26.32 px at 1, 2 and 3 and 20.05 px at 2.625; the 16 px compact title 26.32 px at 1 and 2, 20.05 px at 2.625 and 17.54 px at 3; the 26.32 px display line its own size, except 30.08 px at 2.625. So the noise is as tall as the text or taller, and the line box cuts what does not fit: at a ratio of 1 a 12 px label shows the lower rows of 19 px capitals. The noise sits on the text's baseline snapped to a device pixel. Its glyphs are A to Z, 0 to 9 and `_ - . : =`, packed edge to edge from each word's left edge, each on a device pixel, until the next one would pass the word's end. So the proportional face fits the reserved width, and only the text's own gaps stay. A fifth of the capitals and digits stay whole; the rest keep their top rows, their bottom rows or a middle slice, or lose a band of rows in the middle. Each band is its own clipped box cut on whole modules, so every edge stays on the device-pixel grid. The first version drew lowercase and symbols, one glyph per letter, and only glyphs whose ink fit the box; it read as legible random text, and at a ratio of 1 as stray punctuation, so it was replaced the same day before the user saw it. When Geist Pixel Square is not loaded at the start, `document.fonts.load` runs during the blocks; if the face is still missing at frame 3, the noise frames are skipped and the clean text shows. No fallback face ever draws noise.

   - **Width properties an app may set** (`--popover-width`, `--tooltip-width`, `--toast-width`; rule fixed 2026-11-11 by the CSP check). The component's rule never declares the property. The default is the `var()` fallback in the rule that reads it, as in `max-width: min(var(--popover-width, 360px), …)`. An app sets it with a class on the component and a rule in its stylesheet, and that rule wins at any specificity. The first version declared the property on the component's scoped class (specificity 0,2,0), so a one-class rule in an app lost to it, and the check measured 360px, 280px and 30rem stuck. A `style` passed to the component also works, because it is applied through the CSSOM. The Popover, Toast and Tooltip docs pages show the class form first. A later property an app may set follows the same rule. `--spinner-delay` is a `:root` token, so both forms already worked.
   - **Content Security Policy** (checked 2026-11-11). Hardpoint runs under `style-src 'self'`. Its components never write a static `style` attribute, create a `<style>` element, call `insertRule` or call `setAttribute('style', …)`. Its `style:` directives and spread `style` props go through the CSSOM, which the policy allows. A `style` attribute in an app's own markup is blocked, so an app sets a Hardpoint property with a class (above). Hardpoint renders on the client only, because a server-rendered `style:` value would become an HTML attribute and be blocked. Svelte's runtime does not trip the policy for transitions. bits-ui does write a static `style`, a `<style>` and `insertRule`, and uses `style.cssText`, but only in Command, PinInput and the date-time helpers, which Hardpoint does not use.

It installs the packed tarball into a Vite app that mounts every exported component, `toast()` and `Motion`, serves the app with the production policy and drives the states that create or move elements: each overlay form, a touch swipe on the toast, Combobox filtering, expressive motion and both themes at 1440×900 and 390×844. Exit code 0 means no `securitypolicyviolation` event and no console message about the policy; 1 means a violation; 2 means a step did not reach its state, which counts as unproven. `node run.mjs _control` mounts a static `style` attribute, an injected `<style>` and `setAttribute('style')`, and must report violations, so the detector is known to fire. A full run takes about four minutes. It is the release's consumer test: `npm run consumer` packs the tarball, installs it in `consumer/`, runs svelte-check, builds and runs every scene, then repeats all of it at the Svelte peer floor. The first run on 2026-11-11 was clean for every exported component, and so was the run after Meter, Notice, TextArea, RadioGroup and the CheckboxGroup changes. It mounted no Table with `variant="plain"`. Since 0.3.0 some steps also assert behaviour only the shipped package can prove, and a failed assertion is a failed step (exit 2): closed menus add nothing to `<body>` and the first open plays its entrance (`menus`), the search field's clear button and the hidden native one (`search`), and Button's element and link semantics (`buttons`). Values are omp-remote's light palette except four (the [Tokens](#tokens) table has every value):

## Verification

- **Audit.** `npm run audit` checks every static route at 320x640, 390x844 and 768x1024 with touch, and 1440x900 with a mouse, in the dark theme and then the light one (`--theme dark` or `--theme light` runs one): console errors, horizontal overflow, hit areas (44 px on touch, 24 px with a mouse, sampled with `elementFromPoint` so pseudo-element extensions count), 16 px inputs, text contrast against the composited background, and control boundaries. It exits 1 on any failure; use it as the done-gate for every component and page. It samples 1.5 px inside each edge, so overlaps of 1 px or less pass. The `--motion` pass runs in the dark theme only. `npm run shot` takes `--theme dark|light|system` and `--scheme light|dark` (the device's preference), so `--theme system --scheme light` exercises the system path.
- **Viewports.** Screenshot the specimen route with `shot.mjs` at 320x640, 390x844, 768x1024 and 1440x900. No horizontal overflow except inside data grids; no clipped controls.
- **Phones.** Check touch targets (44 px on coarse pointers, 24 px minimum anywhere), 16 px inputs, safe areas (emulate insets), the on-screen keyboard over forms and sticky bars, sheets and full-screen dialogs, and 200 percent text zoom. Check on a real Android phone; emulation does not show keyboard behaviour reliably. The user has no iPhone (2026-11-11), so iOS zoom and keyboard behaviour stay unverified.
- **Contrast.** Text at least 4.5:1, control boundaries and focus at least 3:1, measured, not assumed.
- **Motion.** Measure durations with Playwright video or rAF timestamps. Confirm the frequency check: no animation that repeats on every key press inside a control, and none on filtering, sorting, paging or route changes; short motion on frequent actions only fades, in 150 ms or less. Check reduced-motion end states and the screen-reader text of decoded strings.
- **Style.** A reviewer compares specimen screenshots with reference frames against the style rules. Layout positions do not need to match the reel. Passing functional checks does not establish the style; the user reviews the look.

## Lessons from moodboard

- Take the style, not the parts. In September the user rejected combining recognisable reference pieces into app screens. In November they rejected the first version of this brief, which listed the reel's elements, SYS BREACH included, as components.
- A showreel is not an app. Its density, type sizes and timings are made to be watched once; check every rule against real use, frequency and phone screens.
- Token swaps over a conventional card or dashboard layout read as generic.
- Build from real frames rather than text briefs or thumbnails.
- Keep chrome quiet. The reel is loud in its transitions, not in permanent banners.
- Model video descriptions get facts wrong; frames and pixels decide.
- Stacked corrections can erase a reference. Each app correction in the first version of this brief was sound alone; together they turned the reel back into the September study, and the user saw it at once in step 1. After each round of corrections, put a screen beside the frames, not just each rule beside the research.

## Decided

The user decided light mode comes later and delegated the rest on 2026-11-09. On 2026-11-10 they added: publishing the package publicly is fine (when they ask for a release), and they move omp-remote to Hardpoint themselves. On 2026-11-11 they decided that data display is built on demand: when an app needs a data component that other apps could share (a data grid, a chart, a chart palette), it is designed then and goes into Hardpoint. A component made for one app stays in that app, built in Hardpoint's style. The same day they put omp-remote's move before topic-map's and chose light mode as the next build.

1. **Selected state: edge marker and tint, never a fill.** A 3 px titanium edge plus a `--surface-selected` tint (`#191712`), in every motion tier. The contract asks for a small marker, research asks for one filled block per view, and the tint reads on phones. The first specimen used `--surface-hover` (`#0A0A0A`, 1.06:1 on black), which nobody could see; the user agreed to the stronger tint on 2026-11-09. An earlier draft put the solid fill in `expressive`; that tier controls motion, and a fill that depends on it would make the same component look different between apps.
2. **Caps labels: kept.** Tracked caps on short fixed labels are the main typographic trait carried from the reel. They stay at 12 px or more, never touch user data, and sit behind `--label-transform` so an app or locale can switch them off. Sources disagree on caps, and none forbids them for short labels.
3. **Type: the three Geist faces.** Geist for UI and reading text, Geist Mono for identifiers and code, Geist Pixel Square for display accents, the spinner and the decode noise. The reel uses pixel glyphs only at moments of change, and the font's published description ([Fontsource](https://fontsource.org/fonts/geist-pixel/about)) says it is made for headlines, logos and other display contexts, so it stays rare. Square matches the reel's square-cornered bitmap glyphs. This keeps omp-remote's rule against pixel text throughout an app. No other display face is added.
4. **Light theme: later.** Dark only in the first milestone. Built in the second milestone on 2026-11-11; dark stays the default.
5. **Name: Hardpoint.** Chosen by the user from four clear options (Hardpoint, Bulkhead, Interlock, Sightline). Datum, Detent, Kerf, Chamfer, Airframe and Burnish were dropped because other UI projects use them.
6. **Header band: `#3A3632`.** The warm-grey match for the reel's `#353734` band: 1.75:1 against black, like the reel's, with `--text` at 9.3:1 and `--muted` at 4.9:1 on it.
7. **One group of solid blocks per view.** The reel fills every button; research says that makes every control look primary. A single primary action, or the header's row of equal-weight page actions, keeps the reel's solid blocks and still shows hierarchy.
8. **Row dividers off by default.** The reel has none (da3-45). A `ruled` variant restores them for long dense tables, where the eye loses its row.
9. **Wordmark: Geist Pixel at 26.32 px.** Its 1 px strokes look thinner than the reel's heavy wordmark; 52.63 px would match but needs a 64 px header. The user accepted the thin wordmark on 2026-11-09.
10. **View title centred.** At 20 px the title is about 1.4 times the row text, against 2.4 times in the reel. The user chose to centre it in the header rather than enlarge it (2026-11-09).
