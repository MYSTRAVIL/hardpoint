# Hardpoint

Hardpoint is the user's shared app design system: a Svelte 5 component library on headless Bits UI. Its style comes from Dan Neuenhaus's MONOLITH reel. Its rules come from real app and phone use.

## Start here

- `docs/BRIEF.md` is the spec. Read it before any design or component work. It holds the user's decisions; where other guidance disagrees, the brief wins.
- Evidence: `docs/ux-research.md`, `docs/elements-da3.md`, `docs/measurements-da3.md` and `docs/reference/da3/`. Evidence explains the rules; it is not a list of things to build.
- The approved appearance contract is in the sibling checkout `../omp-remote/docs/ui-language/BRIEF.md`. Colour tokens came from `../omp-remote/apps/web/public/styles.css`; the brief's Tokens table lists every dark and light value and the ones Hardpoint changed.
- Read `memory/MEMORY.md` before substantive work.

## Commands

- `npm run dev`: dev server. Run it as a managed service and stop it by PID, never by process name.
- `npm run check`: svelte-check, then `scripts/check-lib-imports.mjs` (SvelteKit imports, bits-ui name clashes) and `scripts/check-lib-styles.mjs` (a static `style` attribute in `src/lib` markup, a colour literal in `src/lib` outside `tokens.css`, a colour token missing from a palette block or different between the two light blocks).
- `npm run build`: showcase build, then `prepack` (svelte-package and publint). Never run two builds at once in one checkout.
- `npm run audit [-- routes…] [--serve] [--theme dark|light] [--motion] [--update-baseline]`: the done-gate. It waits until each page has finished its own loading (a page still loading after 10 s fails, unless the baseline marks it `stillBusy`), then checks hit areas, overflow, 16 px inputs, contrast and control boundaries on every route at four viewports, in both themes unless `--theme` picks one, first on the page and then inside every overlay it can open. A route that checks 0 texts fails, and so does a count below half its entry in `scripts/audit-baseline.json`; after changing a page's content on purpose, rerun with `--update-baseline` and commit the file. `--motion` adds the motion pass (dark only). A full URL skips the hydration wait. Exits 1 on failure.
- `npm run shot -- /foundations shots/f.png --serve`: Playwright screenshot. Exits 1 on console errors. For a phone add `--w 390 --h 844 --touch` (coarse pointer, no hover); `--full` captures the whole page; `--theme dark|light|system` picks the theme and `--scheme light|dark` the device preference. In Git Bash, set `MSYS_NO_PATHCONV=1`.
- Review host: when the user should look at a change, `npm run build`, then serve `node node_modules/vite/bin/vite.js preview --host 0.0.0.0 --port 4173 --strictPort` as a persistent managed service and give the URL: the desktop's address on the home network for the phone (in `memory/feedback-host-before-review.md`), `http://localhost:4173` on the desktop. The preview serves the last build, so rebuild after every change. Never ask the user to look without hosting it first.
- `npm run consumer`: the consumer test. Packs the tarball into `consumer/` (a Vite + Svelte app without SvelteKit), then runs svelte-check, a build and every CSP scene under `style-src 'self'`, at the locked Svelte and again at the peer floor; exits 1 on failure. Add a scene for each new component (`consumer/README.md`).
- Release (when the user asks, or when another agent asks for one in a Coral request): bump `version` and turn the `## Unreleased` heading of `CHANGELOG.md` into the version's entry on master, run `npm run check`, `npm run audit -- --serve --motion`, `npm run build` and `npm run consumer`, and commit. Then `node scripts/public-snapshot.mjs "vX.Y.Z"`, `git -c user.name=MYSTRAVIL -c user.email=58272034+MYSTRAVIL@users.noreply.github.com tag -a vX.Y.Z public -m "vX.Y.Z"` (the snapshot's public identity, so the tag carries no private mail address), `git push origin master public vX.Y.Z` and `git push github public:main vX.Y.Z`. The tag starts `.github/workflows/release.yml` on GitHub: it runs the same gates on Linux and publishes the tarball it tested through npm trusted publishing, with provenance and no token or 2FA. Follow it with `gh run watch -R MYSTRAVIL/hardpoint`, then check the version on the registry before telling the user it is out. If the run fails, nothing is published: delete the tag on both remotes and locally, fix on master, and snapshot and tag again. `memory/reference-npm-release.md` has the details when present.
- A Coral request for a release is the user's request (user, 2026-11-12): Coral-spawned sessions run unattended, so do the whole release, pushes included, without asking. Pick the version by semver yourself (before 1.0.0 a change a consumer must adapt to raises the minor version) and reply on the bus with the version and what a consumer must know. Every gate still has to pass; a failed gate stops the release, and the reply says why.

## Rules that are easy to break

- Style, not replica: no SYS BREACH, MONOLITH branding, logistics content or fake telemetry.
- Dark is the default; light comes only through `data-theme` on `<html>`. Colours only through tokens, so both themes follow; a new colour token needs a value in all three palette blocks of `tokens.css`. No hue is a brand colour; red, yellow and green mean status only.
- Type: Geist for UI, reading text and numbers (`tabular-nums`); Geist Mono for identifiers and code; Geist Pixel Square only for the wordmark, one display line per screen, the spinner and decode noise, at multiples of 26.32 px.
- Phones are required: 44 px targets on coarse pointers, 16 px inputs, safe areas, `dvh`, sheets on compact widths.
- Motion is `quiet` by default. `expressive` is opt-in and only for infrequent moments. Honour reduced motion.
- Plain CSS custom properties, no Tailwind. Routes import from `#lib` (SvelteKit 3 removed `$lib`). Files in `src/lib` import each other by relative path and never import `#lib`, `$app/*`, `$env/*` or `@sveltejs/kit`: the package ships only `dist/`, and its consumers (topic-map, omp-remote) are Svelte apps without SvelteKit. `npm run check` fails on such an import.
- No static `style="..."` attribute in component markup: consumers such as omp-remote serve `Content-Security-Policy: style-src 'self'`, which blocks style attributes parsed from markup. `style:` directives and spread `style` props are fine, because Svelte writes them through the CSSOM. A size an app may override is read with a `var()` fallback (`var(--popover-width, 360px)`), never declared on the component's own rule, so an app's class sets it.
- The package is public on npm as `@mystravil/hardpoint` (MIT) since 0.1.0 (2026-11-11). Release only when the user or a Coral request asks, never on your own initiative, an overnight run included. Only the release workflow publishes; nobody runs `npm publish` by hand. The consumer test from the tarball is required, because the repo's own gates read the `.svelte` sources and miss problems in `dist/`. Never `npm unpublish`: fix a broken release with a patch version and `npm deprecate` the broken one.

## Git

Origin is the private Forgejo (`origin`), branch `master`; master holds everything. The public repo is GitHub (`github`, `https://github.com/MYSTRAVIL/hardpoint`, branch `main`). Never push master or a working branch to `github`: it gets only the `public` branch, built by `node scripts/public-snapshot.mjs` from master without `memory/`, `handoffs/`, `overnight/`, `docs/reference/` and the audit reports `docs/audit-*.md`. The script refuses a snapshot with personal identifiers in it (the private Git host, local paths, the personal mail address, private network addresses) and writes its commits as `MYSTRAVIL` with GitHub's noreply address. Commits on `public` before 2026-11-13 carry the personal mail address; rewriting them would need a force push to GitHub. Push `public` to GitHub only for a release or when the user asks. Release tags from `v0.2.1` on sit on `public` commits; `v0.1.0` and `v0.2.0` sit on master and exist only on origin.
